# 构建与发布流程

## 分支约定

- `main`：稳定代码基线。只合入已经完成构建检查、并经过必要实机验证的改动。
- `feature/*`：新功能开发分支。
- `backup/*`、`archive/*`：阶段备份和历史归档，不作为日常开发入口。
- 不要为了整理分支而删除历史分支；确认内容已安全保留后再决定是否清理。

## 日常开发流程

1. 从 `main` 创建独立功能分支。
2. 修改代码时保持改动范围清晰，避免把无关界面或功能混入同一个提交。
3. 提交后运行 Android QA 工作流。
4. 检查工作流所有步骤、单元测试和 APK 上传结果。
5. 在目标电视/盒子上安装对应构建，验证遥控器焦点、确认键、触摸点击和实际数据加载。
6. 实机通过后，将该提交作为新的稳定候选，再合入 `main`。
7. 在版本记录中写明提交 SHA、工作流运行编号、APK 和实测结果。

## GitHub Actions 构建

仓库工作流文件：`.github/workflows/android-qa.yml`

当前 QA 工作流会执行 JavaScript 校验、歌手点歌流程静态检查、自适应电视布局检查、品牌与资源检查、Android 单元测试及 APK 构建/上传。推送到工作流配置的分支时会自动触发，也可在 GitHub Actions 页面手动运行。

手动构建：
1. 打开仓库的 Actions 页面。
2. 选择 **Android QA Build**。
3. 点击 **Run workflow**，选择要构建的分支。
4. 等待状态变为成功后，检查所有步骤。
5. 从 Artifacts 或发布页下载 APK；安装前核对提交 SHA 和构建编号。

## QA 与正式版的区别

- QA/debug 包用于测试，不代表正式签名发布。
- 正式版必须使用受控的签名密钥构建。签名文件和密码只放在安全的本地环境或 GitHub Actions Secrets 中，严禁提交到仓库。
- 正式版发布前必须确认：版本号已递增、Release 构建成功、APK 签名有效、安装升级验证通过、目标设备实测通过。
- 正式版应使用独立的正式 Release 标签（例如 `v1.6.8`，仅在该版本真正发布时创建），并在 Release 说明中附上对应提交 SHA 和变更记录。
- 不要覆盖或删除已发布的稳定 APK；每个构建保留独立版本和下载地址。

## 签名安全

项目 Gradle 从环境变量读取签名参数：

- `KTV_STORE_FILE`
- `KTV_STORE_PASSWORD`
- `KTV_KEY_ALIAS`
- `KTV_KEY_PASSWORD`

签名密钥应至少保留两份安全备份。不要把密码写进脚本、README、提交记录或聊天记录。若签名密钥丢失，后续 APK 可能无法作为原应用无缝升级安装。
